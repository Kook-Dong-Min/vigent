# CPU 스레드 헛돌기 제한 — PyTorch·OpenCV (2026-11-16)

> **이 문서의 수치는 2026-11-16 구성 기준이다.** 개발 노트북 i7-10750H(6코어/논리 12) · GTX 1650 Ti 4GB ·
> torch 2.12.0+cu130(인텔 OpenMP `libiomp5md.dll`) · OpenCV 4.13.0(병렬 프레임워크 Concurrency) · rfdetr 1.12.1 ·
> `detect.imgsz: 320` · `track.algo: ocsort` · 검출 슬롯 person+ppe · `hub.boxed_max_side: 1280` · `hub.boxed_face_side: 640`.
> 실제 서버를 띄워 잰 것이 아니라 저장소의 실제 클래스를 측정 스크립트에서 돌려 쟀다(§6). 구성이 바뀌면 다시 잰다(규칙 9).
> 앞 단계(박스 영상을 표시 크기로 줄이기)의 기록: `boxed_view_resolution_cpu_20261116.md`.

## 0. 한 줄 요약

검출은 GPU 가 하는데 PyTorch CPU 스레드 6개·OpenCV 스레드 12개가 일 없이 대기하며 CPU 를 쓰고 있었다.
스레드 수를 제한하니(PyTorch 1, OpenCV 2) **CPU 점유가 약 3분의 1** 이 됐고, 검출 결과는 완전히 같았고, 검출 갱신은 조금 빨라졌다.

| 1920×1080 · 30장/초 · 박스 영상 시청 중 (3쌍 교대) | 제한 전 | 제한 후 |
|---|---|---|
| CPU 점유(이 프로세스 / 논리 코어 12) | 57.8 ~ 65.5 % | 24.9 ~ 25.3 % |
| 박스 영상 | 13.4 ~ 18.8 장/초 | 18.4 ~ 19.7 장/초 |
| 검출 갱신 | 4.9 ~ 8.3 회/초 | 9.5 ~ 9.8 회/초 |

적용: `config/tuning.yaml` `threads: {torch: auto, opencv: 2}` — **사용자 결정으로 전역 기본 on**. 학원 프로파일은 0(그 기계에서 잰 뒤 켠다).

## 1. 검출 결과는 스레드 수와 무관한가 (`boxed_res_cpu/thread_parity.py parity`, 20:53)

사진 65장(`tests/fixtures` 2 · `demo_assets` 3 · 이 PC 의 `data/evidence` 에서 고르게 60 — 읽기만 함, 640×480·960×540·1920×1080),
장치 cuda, 임계 0.05(박스를 많이 보려고 낮춤). 같은 사진을 ① 기본 스레드 ② 기본 스레드 한 번 더 ③ PyTorch 1개로 돌려 비교.

| 슬롯 | 박스 수 | ①↔② (실행 간 흔들림) | ①↔③ (스레드 6 ↔ 1) |
|---|---|---|---|
| person | 3,024 | 차 0.0 | 박스 수·라벨 동일, 신뢰도·좌표 최대 차 **0.0** |
| ppe | 1,467 | 차 0.0 | 동일, 최대 차 **0.0** |
| fire_smoke | 360 | 차 0.0 | 동일, 최대 차 **0.0** |

- 얼굴 찾기(YuNet): 얼굴 42개, OpenCV 스레드 기본 ↔ 2 ↔ 1 에서 65장 모두 동일(최대 차 0.0).
- 색 변환(`cv2.cvtColor` — 검출 전처리에서 쓰는 유일한 OpenCV 연산): 스레드 수와 무관하게 동일.
- → 정확도 기준선에 영향 없음(평가셋이 이 PC 에 없어 mAP 재측정은 못 했다 — 대신 입력·출력이 같음을 직접 확인).

## 2. 왜 `torch: auto` 인가 — CPU 로 검출하는 기계 (`thread_parity.py cpu`, 20:55)

`VIGENT_DETECT_DEVICE=cpu` 로 강제하고 person 슬롯 검출 1회(wall ms / cpu ms).

| 입력 | 스레드 6(기본) | 2 | 1 |
|---|---|---|---|
| 640×480 | 166.6 / 1,009 | 217.8 / 444 | 354.5 / 350 |
| 1920×1080 | 215.5 / 1,240 | 206.9 / 462 | 371.4 / 398 |

- CPU 로 검출하면 그 스레드가 추론을 한다 — 1개면 **약 2배 느려진다**(167 → 355 ms). 고정 숫자 1 을 기본으로 주면 그런 기계의 검출이 느려진다.
- 그래서 기본값은 `auto`: **검출 모델이 cuda 에 올라갔을 때만** 1개로 줄인다. cpu·mps·onnx-cpu 백엔드는 재지 않았으므로 건드리지 않는다.
  (참고: CPU 검출에서도 스레드 2개는 6개와 시간이 비슷하고 CPU 는 절반 이하였다 — 그 기계에서 잰 뒤 `threads.torch: 2` 처럼 숫자를 직접 적을 수 있다.)

## 5. 저장소 코드로 전·후 (`e2e_cpu.py`, 21:13~21:28)

실제 `worker.Worker` + 캡처 스레드 + 검출(person+ppe, GPU) + `boxed_view.frames` 시청자 1명, 합성 H.264 영상을 30장/초 라이브처럼 주입,
이벤트·알림 기록 차단. 전 = 환경변수 `VIGENT_TORCH_THREADS=0`·`VIGENT_OPENCV_THREADS=0`, 후 = `tuning.yaml` 기본. 전·후를 번갈아 각 20초.
결과에 찍힌 실제 스레드 수: 전 6/12, 후 **1/2**(= 어댑터와 `thread_tune.apply_opencv` 가 실제로 걸었다).

★**이 측정 동안 PC 가 한가하지 않았다.** 아무것도 안 돌려도 PC 전체가 약 2.0코어분을 쓰고 있었다(21:21 — Discord 음성 약 0.7, Steam 0.3,
VS Code 0.2 등). "다른 프로그램" 열이 측정 구간에 이 프로세스 밖에서 쓰인 코어 수다. 그래서 **절대값보다 같은 시간대의 전·후 차이**로 읽는다.

|---|---|---|---|---|---|---|
| 1920×1080 ① | 전 | 60.4 % | 18.1 | 8.0 | 117.9 | 4.23 |

| 1920×1080 ③ | 전 | 57.8 % | 13.4 | 4.9 | 196.7 | 4.93 |

| 640×480 | 전 | 67.4 % | 26.6 | 14.7 | 66.4 | 3.69 |

- CPU 점유: 시청 중 58~67 % → 22~26 %, 허브 닫힘 52 % → 12.5 %.
- 검출 갱신·검출 1회 시간: 6쌍 모두 "후"가 같거나 빠르다. 박스 영상 장수: 5쌍 중 4쌍 같거나 높고 1쌍(2304×1296)은 15.2 → 14.6 으로 낮다(그 "후" 실행의 배경 부하가 더 컸다).
- "다른 프로그램" 이 "전"에서 더 크게 찍힌다(3.4~4.9 vs 1.7~3.6). 배경 부하 자체가 흔들린 것인지, 헛도는 스레드가 시스템 쪽 부하를 늘린 것인지는 **가려내지 못했다.**
- "후"는 세 번의 1920×1080 실행이 거의 같다(24.9~25.3 %, 18.4~19.7 장, 9.5~9.8 회) — 배경 부하에 덜 흔들린다.

### 신뢰 낮은 묶음(참고만) — 21:05~21:11, 배경 부하 기록 없이 잰 첫 묶음

| 조건 | 전 → 후 CPU | 박스 영상 | 검출 갱신 |
|---|---|---|---|
| 640×480 | 61.8 → 21.8 % | 23.3 → 22.0 | 13.7 → 16.0 |
| 1920×1080 | 44.7 → 22.0 % | 13.2 → 11.5 | 5.9 → 7.3 |
| 2304×1296 | 64.5 → 24.7 % | 15.6 → 13.5 | 6.9 → 6.8 |

- 같은 설정을 20:39 에 쟀을 때(§4, 1920×1080 23.8 장)·21:13 이후(18.4~19.7 장)보다 박스 영상 장수가 크게 낮다 — 그때 PC 에서 무엇이 돌았는지 기록이 없다.
  이 묶음을 보고 측정기에 "다른 프로그램 코어 수"·"기계 속도 지표"를 넣었다. CPU 점유가 내려간 것은 이 묶음에서도 같다.
  **박스 영상 장수는 배경 부하에 따라 11.5 ~ 23.8 장/초까지 흔들렸다**(같은 설정) — 장수의 절대값은 이 정도 폭으로 읽는다.

## 6. 적용한 것 · 되돌리기 · 재지 못한 것

- `vigent-core/thread_tune.py`(신규): 설정 해석 · `apply_torch(device)` · `apply_opencv()` · `status()`. 건 뒤 다시 읽어 확인하고, 실패해도 예외를 올리지 않는다.
- `detectors/rfdetr_adapter.py`: 모델을 올린 장치로 `apply_torch` 호출 · `main._startup`: `apply_opencv` 호출(선택 서비스) · `/health`: `cpu_threads`.
- `config/tuning.yaml` `threads: {torch: auto, opencv: 2}` · 학원 프로파일 `{torch: 0, opencv: 0}`(intent 선언).
- 실제 기동 함수(`main._startup`, 카메라·모델 미기동)로 확인: OpenCV 스레드 12 → 2, `/health` `cpu_threads.opencv.applied = true`(21:29).
- 되돌리기: `threads.torch: 0`·`threads.opencv: 0`(서버 재시작) 또는 환경변수 `VIGENT_TORCH_THREADS=0` `VIGENT_OPENCV_THREADS=0`.
- 테스트: `tests/test_thread_tune.py`(29건).

재지 못한 것:
- 실제 서버(uvicorn)·실제 브라우저·실제 카메라(웹캠·RTSP) — 미측정. 측정 영상에 사람이 없어 자세 추정·머리 모자이크 비용도 빠져 있다.
- 카메라 여러 대 — 미측정(1대만).
- 학원 노트북 — 미측정(그래서 프로파일은 끔).
- CPU 검출 기계·mps·onnx-cpu 백엔드에서의 효과 — §2 의 낱개 측정 외에는 미측정(auto 는 건드리지 않는다).
- 한가한 PC 에서의 재측정 — §5 는 배경 부하 약 2코어분이 있는 상태다.

## 7. 다시 재는 법

```powershell
# 게임·메신저 통화·다운로드 등 CPU/GPU 를 쓰는 프로그램을 끄고(결과의 other_cores 가 작아야 한다)
$o = "$env:TEMP\boxed_res_cpu"; mkdir $o -Force
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\measure_res_cpu.py . $o          # 시험 영상 t_*.mp4 를 만든다
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\thread_parity.py . parity 60     # §1
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\thread_parity.py . cpu           # §2
$env:VIGENT_TORCH_THREADS="0"; $env:VIGENT_OPENCV_THREADS="0"                       # §5 전
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\e2e_cpu.py . $o\t_1920x1080.mp4 before 1
Remove-Item Env:VIGENT_TORCH_THREADS, Env:VIGENT_OPENCV_THREADS                     # §5 후(설정 파일대로)
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\e2e_cpu.py . $o\t_1920x1080.mp4 after 1
.\.venv\Scripts\python.exe benchmarks\boxed_res_cpu\e2e_cpu.py . $o\t_1920x1080.mp4 cv4 1 1 4   # §4(스레드 수 직접 지정)
```

원본 결과: `boxed_res_cpu/result_e2e_threads_20261116.json`(§1·§2·§4·§5) · `boxed_res_cpu/result_fix_options_20261116.json`(§3).
