# 박스 영상 — 해상도별 CPU 비용과 "표시 크기로 줄여 처리" (2026-11-16)

> **이 문서의 수치는 2026-11-16 구성 기준이다.** 개발 노트북 i7-10750H(6코어/논리 12) · GTX 1650 Ti 4GB ·
> torch 2.12.0+cu130 · OpenCV 4.13.0 · rfdetr 1.12.1 · `detect.imgsz: 320` · `track.algo: ocsort` · 검출 슬롯 person+ppe.
> 실제 서버를 띄워 잰 것이 아니라 **저장소의 실제 함수·클래스**를 측정 스크립트에서 직접 돌려 쟀다(§5·§7).
> 구성(해상도·스레드·모델)이 바뀌면 다시 잰다(CLAUDE.md 규칙 9).

## 0. 한 줄 요약

웹캠보다 해상도가 높은 영상이 들어오면 박스 영상이 끊기고 검출이 느려졌다. 원인은 박스 영상 1장마다 **원본 크기 그대로**
얼굴 찾기(YuNet)를 돌린 것 — 비용이 화소 수에 비례한다(640×480 30 ms/장 → 1920×1080 212 ms/장).

조치(적용): 박스 영상을 만들 때 프레임의 **긴 변**이 `hub.boxed_max_side`(1280)를 넘으면 줄이고, 얼굴 찾기는
`hub.boxed_face_side`(640) 이하 사본으로 한다. 검출·판정·증거 사진은 원본 크기 그대로다.

결과(§5, 1920×1080 · 30장/초 · 박스 영상 시청 중):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 박스 영상 | 3.6 장/초 | 19.1 장/초 |
| 검출 갱신 | 6.6 회/초 | 8.3 회/초 |
| **CPU 점유** | **75.0 %** | **72.2 %** |

★**끊김·검출 지연은 고쳐졌지만 CPU 점유율은 그대로다.** 점유율의 대부분은 해상도와 무관한 **스레드 헛돌기**(§3)이고,
640×480 에서도 74~77% 다. 측정기 안에서 스레드 수만 제한하니 72% → 25% 로 내려갔다(§5 마지막 표).
→ **[같은 날 후속] 스레드 제한은 `threads:` 설정으로 저장소에 적용됐다** — 근거·전후 측정: `cpu_thread_limit_20261116.md`.
  이 문서의 "미적용" 표기는 이 문서를 쓴 시점(20:44) 기준이다.

## 3. 스레드 헛돌기 — 해상도와 무관한 낭비 (다음 단계, **미적용**)

CPU 시간이 벽시계의 약 6배로 나와 스레드 수를 바꿔 비교했다. 속도는 같고 CPU 만 달랐다(`measure_fix_options.py`).

- 논리 코어 12개 PC 에서 5코어 = 작업 관리자 약 42%.
- 원인 가설(미검증): 검출은 GPU 가 하는데 PyTorch CPU 스레드 6개가, YuNet 은 OpenCV 스레드 12개가 대기하며 CPU 를 쓴다
  (onnxruntime 에서 같은 병을 고친 전례: `ort_tune.py` Q9/Q10). 스레드 수에 따른 CPU 변화는 실측, 내부 원인은 추정.
- GPU 없이 CPU 로 검출하는 기계에서는 스레드를 줄이면 검출이 느려진다 → 적용한다면 기본값은 그대로 두고 프로파일별로 켠다.

### 5-2. 서버 구성 전체 (`boxed_res_cpu/e2e_cpu.py`)

실제 `worker.Worker` + 캡처 스레드(`_StreamCapture`) + 검출(person+ppe, GPU) + `boxed_view.frames` 시청자 1명.
카메라는 합성 H.264 시험 영상을 **30장/초 라이브처럼** 흘려 넣었다(`worker._open_capture` 만 대역, 사용자 웹캠 미사용,
이벤트·알림 기록 차단). 각 20초 1회. CPU 점유 = 프로세스 CPU초/벽시계초 ÷ 논리 코어 12.
**사람이 없는 합성 영상이라 자세 추정·머리 모자이크 비용은 빠져 있다. HTTP 서버·브라우저도 포함되지 않는다.**
